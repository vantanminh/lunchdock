# CLI uses API tokens and polls deployments

## Context

Operators want to deploy from CI and a terminal without opening the panel.
The panel already has scoped API tokens (`read`/`write`) and an HTTP API for
every action, and deployments are recorded with their build and rollout log.
Cookie sessions need CSRF tokens and TOTP, which are awkward in scripts.

## Decision

`rudder` is a thin client of the public `/api/v1` API and authenticates only
with `rdr_` API tokens sent as a bearer header. `rudder login` checks the token
against `/api/v1/me` and stores the URL and token in
`~/.config/rudder/config.json` with mode 0600; `RUDDER_URL` and `RUDDER_TOKEN`
override it. The token is read from the environment or stdin, never from an
argument, so it does not land in shell history or `ps`.

`rudder deploy` starts the same deploy, build, or stack-up call the UI uses and
then polls the service's deployment list every two seconds, printing new log
lines until the deployment finishes. `rudder logs -f` polls the log search API
the same way. Only a `succeeded` deployment exits 0. `rudder cache purge` calls
the existing purge endpoint. No new server endpoints or streaming protocols.

## Consequences

- The CLI cannot do anything the token's scope does not allow; read tokens can
  list and tail logs but get a 403 on deploy and purge.
- Polling adds up to two seconds of latency to log output and costs one small
  request per interval, which is fine for a single operator.
- Every CLI path is covered by tests against a real panel on a TCP socket; image
  and stack deploys run against Docker only with `RUDDER_DOCKER_TESTS=1`.
